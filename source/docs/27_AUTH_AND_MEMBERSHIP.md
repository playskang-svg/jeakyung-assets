# 인증과 회원 관리

## 원칙

- 그룹웨어는 재경닷컴 임직원 전용이다.
- Supabase Auth를 이메일·비밀번호 인증 공급자로 사용한다.
- 비로그인 사용자는 보호 경로와 내부 데이터를 사용할 수 없다.
- 인증 여부와 회원 상태를 모두 통과해야 하며 UI 표시만으로 권한을 판정하지 않는다.

## 회원 상태

| 상태 | 의미 | 내부 접근 |
| --- | --- | --- |
| `pending` | 가입 신청 후 관리자 검토 전 | 금지 |
| `approved` | 승인되고 사용 가능한 계정 | 역할·권한에 따라 허용 |
| `rejected` | 가입 신청 거절 | 금지 |
| `locked` | 보안 또는 관리자 조치로 잠김 | 금지 |
| `resigned` | 퇴사 등으로 이용 종료 | 금지 |

## 지원 기능

- 로그인·로그아웃
- 가입 신청, 관리자 승인·거절, 승인 대기
- 비밀번호 재설정·변경
- 마이페이지와 프로필 수정
- 계정 잠금·해제
- 퇴사·탈퇴의 비활성화와 보관
- 로그인 성공·실패·로그아웃 기록

## 가입 데이터

- 이름, 회사 이메일, 연락처, 부서, 직급·직책을 신청 정보로 받는다.
- 비밀번호는 Supabase Auth에만 전달하며 애플리케이션 테이블이나 로그에 저장하지 않는다.
- 회사 이메일 허용 도메인과 연락처 보유 기간은 `[미정]`이다.
- 가입 시 이름·연락처·희망 조직은 신청 정보일 뿐 권한 판정에 사용하지 않는다.
- 최종 조직과 역할은 관리자 승인 RPC가 확정한 값만 신뢰한다.

## G2 구현

- `AuthProvider`가 초기 세션, 인증 변경 구독, 프로필·역할, 로딩·오류와 복구 상태를 관리한다.
- 가입은 `signUp`, 로그인은 `signInWithPassword`, 로그아웃은 현재 기기의 `signOut`, 재설정은 `resetPasswordForEmail`과 `updateUser`를 사용한다.
- 비로그인은 로그인, 승인 대기는 pending, 거절·잠금·퇴사는 각각 상태 안내로 이동한다.
- 승인 계정만 내부 App Shell을 사용하며 관리자 경로는 `admin` 또는 `super_admin` 역할을 추가 확인한다.
- 실제 Supabase 프로젝트 연결과 통합 인증 검증은 프로젝트 값·Redirect 설정 후 완료한다.

보안 판정과 RLS는 [`31_SECURITY_AND_RLS.md`](31_SECURITY_AND_RLS.md), 관리자 조치는 [`32_ADMIN_SYSTEM.md`](32_ADMIN_SYSTEM.md)를 따른다.

## G3 보완: 직원 프로필

- 가입 신청은 기존 조직 선택과 함께 입사일, 사번, 관리자 확인 메모, 선택 프로필 사진을 받는다. 부서·직급·직책·입사일·사번은 승인 단계에서 관리자가 최종 확정한다.
- `profiles`의 공식 이름·회사 이메일·사번·조직·입사일·재직 상태·역할은 관리자 관리 필드다. 본인은 표시 이름, 휴대전화, 사무실 전화, 내선번호, 한 줄 소개와 프로필 사진만 수정한다.
- 회사 이메일 표시값을 수정해도 Supabase Auth 이메일은 변경하지 않는다. 인증 이메일 변경 절차는 별도 Phase로 보류한다.
- 계정 상태(`membership_status`)와 재직 상태(`employment_status`)를 분리한다. 퇴사 재직 상태는 내부 권한 판정에서 차단한다.
- 프로필 사진은 가입 시 일회성 24시간 업로드 토큰 또는 승인 후 사용자 JWT로 Edge Function을 통과하며, 비밀번호·세션 토큰은 애플리케이션 데이터에 저장하지 않는다.
