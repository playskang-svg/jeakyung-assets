# 역할과 권한 매트릭스

## 역할

1. `super_admin` — 최고 관리자
2. `admin` — 관리자
3. `department_head` — 부서장
4. `team_lead` — 팀장
5. `employee` — 직원

역할은 직급·직책과 별개다. 한 사용자의 최종 권한은 역할, 소속 조직, 리소스별 정책과 명시적 예외를 서버에서 조합해 판정한다.

## 판정 원칙

- 메뉴를 숨기는 것은 편의 기능이며 보안이 아니다.
- 클라이언트, 서버 함수와 Supabase RLS가 동일한 권한 개념을 사용한다.
- 기본값은 거부이며 명시적으로 허용된 작업만 수행한다.
- 최고 관리자 권한 부여·회수, 최종 삭제와 권한 변경은 재인증과 감사 로그를 요구한다.
- 한 사용자는 여러 역할을 가질 수 있으며 `user_role_assignments`의 `(user_id, role_code)`를 유일하게 유지한다.
- 일반 관리자는 `admin`, `super_admin`을 부여할 수 없고 최고 관리자만 관리자 계열 역할을 부여한다.
- 기본 역할을 자동 부여하지 않으며 첫 최고 관리자는 별도 1회성 SQL로만 부트스트랩한다.
- 관리자 메뉴는 Auth Context의 DB 역할로 표시하고 직접 URL은 관리자 Route와 RLS·RPC가 다시 차단한다.

게시판별 권한은 [`29_BOARD_SYSTEM.md`](29_BOARD_SYSTEM.md), 서버 보안은 [`31_SECURITY_AND_RLS.md`](31_SECURITY_AND_RLS.md)를 따른다.

## 유효 역할 정책

2026-08-15부터 사용자 역할 전환을 제공하지 않는다. 전환 전에는 관리자 메뉴가 막혀 관리 기능을 빠뜨리는 문제가 있었고, 한 사람이 여러 모드를 오갈 업무상 이유가 없다.

- 사용자는 활성 상태의 여러 배정 역할을 보유하되 권한 합산 없이 **보유 역할 중 가장 높은 역할** 하나로 업무 권한을 판정한다. 상위 여부는 `roles.sort_order`가 작을수록 상위다(`super_admin` 10 → `employee` 50).
- 유효 역할은 `get_user_active_role()`이 매번 계산한다. RLS 전반이 `has_role()`을 통해 이 함수만 거치므로 화면에 보이는 메뉴와 서버가 허용하는 작업이 어긋나지 않는다.
- 모든 승인 직원은 최소 `employee` 역할을 유지한다.
- 사용자는 자신의 보유 역할을 확인만 하고 바꾸지 않는다. `set_my_active_role`은 `authenticated`에서 실행 권한을 회수했다. 클라이언트 state와 localStorage는 권한 근거가 아니다.
- `admin`·`super_admin` 역할을 보유하면 로그인 즉시 관리자 메뉴가 보이고 관리 기능을 사용한다. 나머지 업무는 같은 계정의 일반 메뉴로 처리한다.
- 역할 해제 시 유효 역할은 남은 역할 중 최상위로 자동 이동한다. 마지막 최고 관리자 역할 해제와 마지막 최고 관리자의 퇴사 처리는 차단하고 시도 자체를 감사 로그에 남긴다.
- `user_active_roles`와 `profiles.preferred_start_role`은 권한 판정에 쓰지 않는다. 기존 함수가 계속 기록하므로 테이블은 남겨 두되 과거 값으로 읽지 않는다.
